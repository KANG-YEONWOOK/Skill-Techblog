# Fixed window에서 token bucket으로: rate limiter 교체 후 p99 latency가 1,850ms에서 420ms로 줄어든 사례

공개 API에서 throttle된 클라이언트들이 윈도가 열리는 순간 한꺼번에 재시도하면 gateway에는 평균 부하의 몇 배가 한 번에 들어옵니다. 한 내부 엔지니어링 노트(2026)는 fixed window 방식의 rate limiter를 token bucket으로 바꾸고 그 효과를 롤아웃 2주 뒤에 측정했습니다.

이 글에서는 노트가 설명하는 문제와 새 설계, 측정 결과와 한계를 정리합니다. 결론부터 말하면 초당 최대 부하는 4,800건에서 1,400건으로, gateway p99 latency는 1,850ms에서 420ms로 내려갔습니다.

## 윈도 시작 순간에 몰리는 요청

노트의 API는 클라이언트마다 60초 윈도에 600건을 허용하는 fixed window rate limiter를 썼습니다. 한도에 걸린 클라이언트는 윈도가 새로 열리는 시점에 맞춰 다시 요청을 보냈고 그 시점이 모두 같았습니다.

그 결과 윈도의 첫 1초에 최대 4,800 requests/s가 몰렸습니다. 평균 부하는 900 requests/s였습니다. 이 burst 때문에 gateway의 p99 latency가 1,850ms까지 올랐습니다.

## 클라이언트별 token bucket

새 설계는 클라이언트마다 token bucket을 둡니다. 버킷은 token을 최대 100개 담고 초당 10개씩 채웁니다. 장기 한도는 분당 600건으로 기존과 같습니다.

버킷 상태는 Redis에 있고 확인과 차감은 Lua script 하나로 atomic하게 처리합니다. gateway 인스턴스가 둘 이상이어도 같은 token을 두 번 쓸 수 없습니다. 요청이 거절되면 응답에 Retry-After 헤더가 붙고 값은 다음 token이 생길 때까지의 시간으로 계산합니다.

## 롤아웃 2주 후 측정 결과

노트는 같은 트래픽 수준에서 롤아웃 2주 뒤의 값을 비교합니다.

| 항목 | 이전 | 이후 |
| --- | --- | --- |
| 초당 최대 부하 (requests/s) | 4,800 | 1,400 |
| gateway p99 latency (ms) | 1,850 | 420 |
| 거절된 요청의 비율 | 2.1% | 2.6% |
| Redis CPU 사용량 | 기준 | +8%p |

거절 비율은 0.5%p 올랐습니다. 윈도 경계에서는 클라이언트가 한도를 넘겨 보낼 수 있었는데 token bucket에서는 그럴 수 없기 때문이라고 노트는 설명합니다. Redis CPU 사용량은 8%p 늘었습니다.

## 남은 한계

token bucket은 서로 다른 많은 클라이언트가 같은 순간에 시작하는 상황에는 도움이 되지 않습니다. 노트에 따르면 배포 직후에는 짧은 burst가 여전히 보입니다.

테스트 범위도 제한적입니다. 활성 클라이언트가 50,000을 넘는 환경에서는 이 설계를 검증하지 않았습니다. Retry-After를 무시하고 즉시 재시도하는 클라이언트도 그대로 남아 있습니다.

## 마치며

노트의 변경은 한도(분당 600건)를 그대로 두고 허용하는 방식만 바꿨습니다. 같은 트래픽에서 초당 최대 부하가 4,800건에서 1,400건으로 줄었고 그 대가로 거절 비율이 2.1%에서 2.6%로, Redis CPU가 8%p 올랐습니다. 클라이언트 수가 50,000을 넘을 때의 동작과 배포 직후의 동시 시작 burst는 노트에서도 열린 문제로 남아 있습니다.
