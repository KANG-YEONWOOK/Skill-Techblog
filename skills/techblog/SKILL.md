# techblog

이 스킬은 자료를 읽고 그 핵심을 한국어 기술 블로그 아티클로 쓴다. 글의 독자는 자료의 분야를 아는 개발자이고, 글은 토스, 카카오, 당근 기술 블로그에 실린 글처럼 읽혀야 한다. 글의 모든 문장은 따로 읽어도 무엇에 대한 말인지 알 수 있어야 한다.

글은 초안과 후처리로 나눠 쓴다. 1~5단계에서는 모든 글에 같은 규칙으로 초안을 쓰고 점검한다. 6단계(후처리)에서는 초안을 이 글의 독자 입장에서 다시 읽고 이 글에 맞게 고친다.

입력: $ARGUMENTS

## 인자 해석

- 입력에 `casual`, `Casual`, `해요체`가 있으면 Casual 글을 쓴다. `default`, `Default`, `합니다체`가 있거나 어투를 지정하지 않았으면 Default 글을 쓴다.
- `-o <경로>`는 글을 저장할 파일 경로다. 이 인자가 없으면 현재 작업 디렉터리에 글 주제를 나타내는 영문 kebab-case 이름(예: `cache-invalidation-latency.md`)으로 저장한다.
- `--retone`이 있으면 입력 파일을 완성된 아티클로 보고 7단계(어투 적용)만 한다. 6단계(후처리)는 하지 않는다. `--retone` 없이 이미 쓴 글의 어투만 바꿔 달라고 요청해도 `--retone`으로 본다. 출력 경로가 없으면 `<입력 이름>.<casual|default>.md`에 저장한다.
- `--keep-work`가 있으면 작업 파일을 지우지 않는다.
- 나머지 입력은 자료(파일 경로, URL)와 추가 지시(독자, 분량, 강조할 부분)다. 입력에 자료가 없으면 대화에 붙여넣은 텍스트를 자료로 쓴다. 붙여넣은 텍스트도 없으면 무엇을 정리할지 사용자에게 묻는다.

## 파일

- 글은 `<이름>.md`에 저장한다.
- 작업 파일은 출력 파일과 같은 폴더에 만든다. fact sheet는 `<이름>.facts.md`이고, Casual 글을 쓸 때만 만드는 Default 초안은 `<이름>.draft.md`다. 6단계를 시작할 때 스크립트가 후처리 전 초안을 `<이름>.unrevised.md`에 복사해 둔다. 작업 파일은 8단계에서 지운다.
- 후처리 대상은 합니다체 글이다. Default 글이면 출력 파일 `<이름>.md`, Casual 글이면 Default 초안 `<이름>.draft.md`다.

## 스크립트 실행

- 검사 스크립트는 Bash 도구로 실행한다. Windows에서는 `python`, macOS와 Linux에서는 `python3`를 쓴다. 경로는 큰따옴표로 감싼다. 한 번에 명령 하나만 실행하고, `;`나 `&&`로 다른 명령(`cat` 등)을 이어 붙이지 않는다. 이 스킬이 허용하는 Bash 명령은 아래 검사 스크립트뿐이다. 참고 문서와 PDF는 Read 도구로 읽고, 파일 목록은 Glob 도구로 본다.
  - 문체 검사: `python "${CLAUDE_SKILL_DIR}/scripts/lint_ko.py" "<글>" --tone default --facts "<이름>.facts.md"`
  - 후처리: `python "${CLAUDE_SKILL_DIR}/scripts/revise_ko.py" start "<후처리 대상>"`, 같은 스크립트의 `repeats "<후처리 대상>"`, `check "<후처리 대상>"`
  - 어투 검사: `python "${CLAUDE_SKILL_DIR}/scripts/tone_check.py" "<이름>.draft.md" "<이름>.md"`
  - 작업 파일 삭제: `python "${CLAUDE_SKILL_DIR}/scripts/tone_check.py" --cleanup "<이름>.facts.md" "<이름>.draft.md" "<이름>.unrevised.md"`
- Python이 없거나 Bash를 쓸 수 없으면 `references/rubric.md`의 Gate와 자동 측정 항목을 직접 세서 같은 기준으로 점검한다.

## 작업 순서

### 1. 자료 읽기

- PDF는 Read 도구로 읽는다. 한 번에 읽히지 않을 만큼 길면 `pages`로 나눠 마지막 쪽까지 읽는다. 표, 그림 설명, 부록의 수치도 읽는다.
- URL은 WebFetch로 가져온다. HTML 페이지는 "요약하지 말고 본문을 그대로 돌려 달라"고 요청하고, 본문이 길면 절 단위로 나눠 요청한다. PDF URL을 WebFetch로 가져오면 로컬에 `.pdf` 파일이 저장되므로 그 파일을 Read로 읽는다. 논문 초록 페이지(arXiv의 `/abs/` 등)를 받았다면 본문이 있는 PDF나 HTML 링크를 찾아 그 문서를 읽는다.
- 자료가 여러 개면 모두 읽는다.

### 2. fact sheet 쓰기

fact sheet(`<이름>.facts.md`)에는 아래 항목을 적는다. 글에 쓰는 수치, 주장, 측정 대상의 이름은 이 파일에서만 가져온다.

- 핵심 주제: 파일 맨 위에 "이 글을 읽은 독자가 알게 될 것"을 한 문장으로 적는다.
- 자료 정보: 제목, 저자나 기관, 연도, URL을 적는다.
- 문제와 배경: 자료가 풀려는 문제와 기존 방법의 한계를 적는다.
- 방법: 핵심 아이디어, 동작 순서, 실험 설정(모델, 데이터, 조건)을 적는다.
- 수치: 수치마다 무엇을 잰 값인지, 값, 단위, 조건, 비교 대상, 원문 표현을 적는다.
  - 비교 기준이 헷갈리기 쉬운 수치는 원문 문장을 그대로 옮겨 둔다. 예를 들어 "at most 20% of the baseline"은 "기준값의 20% 이하"이지 "기준값보다 20% 이하"가 아니다.
  - 글에서 단위를 바꾸거나 반올림할 값은 바꾼 값도 함께 적는다.
  - "수십만", "수천"처럼 어림한 수량을 쓸 거라면 그 근거가 되는 원문 표현과 함께 적는다.
- 한계: 자료가 밝힌 한계와 실험 범위를 적는다.
- 용어: 원어와 이 글에서 쓸 표기를 적는다.
- 인용할 문장: 원문을 그대로 옮기고 위치(쪽, 절)를 적는다.

### 3. 개요 잡기

- `references/style-guide.md`를 읽는다.
- fact sheet 맨 위의 핵심 주제를 기준으로 제목, 도입 방식, H2 절 4~7개를 정한다. 각 절이 핵심 주제의 어느 부분을 설명하는지, 각 절에 fact sheet의 어느 항목을 쓸지 정한다.

### 4. Default 초안 쓰기

Casual로 요청받아도 초안은 먼저 합니다체로 쓴다. Casual 글이면 초안을 `<이름>.draft.md`에 쓰고, Default 글이면 출력 파일에 바로 쓴다.

자료에 충실하게 쓰기

- 자료에 있는 사실만 쓴다. 자료에 없는 수치, 사례, 출처, 전망을 만들지 않는다.
- 사실을 전하는 문장은 기술, 방법, 결과를 주어로 쓴다. 예: "배치 크기를 줄인 설정은 p99 지연을 0.8초로 낮췄습니다". "저자들은", "논문은", "원문은"은 저자의 주장, 추정, 판단을 옮길 때만 쓰고, 이런 문장은 본문 문장의 6%를 넘기지 않는다. 자료를 "제공된 자료", "주어진 글"로 부르지 않는다. 글쓴이가 직접 해 본 것처럼 쓰지 않는다.
- 자료에 없는 값은 쓰지 않는다. 그 값이 자료에 없다는 문장도 본문의 설명 중간에 쓰지 않는다. 독자가 결과를 자기 환경에 옮길 때 필요한 조건(실험하지 않은 환경, 밝히지 않은 비용)이 자료에 없으면 그 사실은 한계 절이나 "마치며"에 쓴다.
- "모두", "항상", "전혀", "유일한", "~뿐", "오직" 같은 범위 표현과 "자주", "대부분", "몇 문단마다" 같은 빈도 표현은 자료가 그렇게 쓴 경우에만 쓴다. 자료가 예시 하나로 보여 준 현상을 "~할수록 ~하다" 같은 일반 법칙으로 바꾸지 않는다.
- 자료를 옮기기만 하지 않고 자료를 읽은 사람의 분석을 넣는다. 분석은 설계 이유, 표에서 읽히는 수치 차이, 독자가 자기 환경(한국어 데이터, 서비스 규모, 비용)에 옮길 때 달라지는 점이다. 분석은 자료의 동작 방식과 조건에서 추론하고, 추론이라는 것을 문장에 드러낸다. 독자 환경에 대한 내용도 "~라면", "~수 있습니다"처럼 조건이나 가능성으로 쓴다. 분석 문장에도 수치 비교나 조건 같은 새 정보가 있어야 한다.

문장을 따로 읽어도 이해되게 쓰기

- 문장마다 무엇에 대한 문장인지 쓴다. 바로 앞 문장과 주어가 같으면 주어를 뺀다. 새로 쓰는 주어는 기술, 설정, 지표의 이름으로 쓴다.
- 수치를 쓰는 문장에는 그 수치가 무엇을 잰 값인지, 어떤 조건에서 잰 값인지, 무엇과 비교한 값인지를 같은 문장에 쓴다.
- "이", "그", "둘", "차이" 같은 말은 가리키는 대상이 바로 앞 문장에 있을 때만 쓴다. 절이 시작하는 곳과 표, 목록, 코드 블록 바로 뒤에서는 대상의 이름을 쓴다.
- 괄호에는 원어, 약어 풀이, 단위 변환만 넣고, 조건과 설명은 문장으로 쓴다. 여러 명사는 쉼표로 나열하거나 문장으로 쓴다.
- 어떤 헤딩 아래의 첫 문단이든 앞 절을 읽지 않은 독자가 이해할 수 있게 쓴다.

글의 구성

- 도입은 자료의 구체 장면이나 독자가 겪는 상황에서 시작한다. 구체 장면은 요청 하나, 입력 하나, 장애 하나처럼 한 가지 경우에 무엇이 일어났는지를 보여 준다. 첫 문단에 수치를 연달아 늘어놓지 않는다.
- 도입의 "이 글에서는 ~를 정리합니다" 문장은 핵심 주제를 한 문장으로 말하고, 다룰 항목을 셋 이상 늘어놓지 않는다.
- "표를 보면", "결론부터 말하면" 같은 이끄는 말은 글 전체에서 한두 번만 쓴다. "결론부터 말하면"은 쓰지 않아도 된다. "짚어 둘 점이 세 가지 있습니다"처럼 나열을 예고하는 문장은 쓰지 않는다.
- 헤딩은 다루는 내용을 특정한다. "적용할 때 따져 볼 점" 같은 일반적인 헤딩 대신 "한국어 서비스에 옮긴다면", "블록 크기를 정할 때"처럼 그 절의 내용을 쓴다. 헤딩은 명사구, "~하기", "~할까" 질문으로 쓰고, 합니다체나 해요체 종결을 헤딩에 쓰지 않는다.
- 분량은 논문 한 편이면 공백 제외 5,000~10,000자로 쓴다. 분량을 줄이느라 핵심 실험, 설계 이유, 자료의 표, 의사 코드, 설정을 빼지 않는다. 핵심 주제를 설명하지 않는 세부는 뺀다.
- "마치며" 절은 3~5문장으로 쓴다. 본문을 다시 요약하지 않는다. "마치며"에는 독자가 이 자료를 자기 일에 쓸 때 판단할 기준(결론이 성립하는 조건, 실험 범위)과 자료가 밝힌 한계나 후속 연구를 쓴다. 자료가 열린 질문이라고 하지 않은 내용을 열린 질문으로 쓰지 않는다.
- 글 마지막에 "참고자료" 절을 둔다.

문장과 문단

- 주장은 바로 쓴다. 아무도 하지 않은 주장을 먼저 부정한 뒤 고쳐 말하지 않는다.
- 평가어 대신 자료의 수치와 이름을 쓴다. 중요하다고 말하는 대신 왜 중요한지(비용, 수치, 실패 조건)를 쓴다.
- 비유 대신 대상과 수치를 직접 쓴다. 예: "캐시가 트래픽을 떠받친다" 대신 "읽기 요청의 90%를 캐시가 처리한다".
- 기본 동사(이다, 있다, 쓰다, 늘다, 줄다, 보다, 바꾸다)를 쓴다.
- 문장 길이와 종결을 섞는다. 사실 하나만 전하는 문장은 짧게 쓰고 짧은 문장에도 주어를 쓴다. 사람 글에서 35자 미만인 문장은 문장의 12~25%다. 같은 종결("~했습니다")이 네 문장 넘게 이어지지 않게 하고, 한 종결이 서술 문장의 절반을 넘지 않게 한다. 동작을 설명하는 "~합니다/~됩니다"만 이어지기 쉬우므로 상태 문장("기본 블록 크기는 16입니다"처럼 주어가 있는 ~입니다 문장), 존재 문장(~있습니다), 가능성 문장(~수 있습니다), 과거 문장(측정했습니다, 보고했습니다)을 섞는다. Casual 글의 종결 다양성도 이 초안에서 정해진다.
- 문단은 2~3문장 단위로 나눈다. 사람 글은 문단당 평균 2문장이고 문단의 27~52%가 한 문장 문단이다. 네 문장 넘게 이어지는 문단은 내용이 바뀌는 곳(새 사실, 새 수치)에서 나눈다. 한 문장 문단에는 수치, 정의, 조건 같은 사실을 쓴다. 앞 문단을 정리하는 문장이나 다음 내용을 예고하는 질문을 한 문장 문단으로 만들지 않는다. 문단을 나눌 때 문장을 짧게 자르지 않는다.
- 문단은 그 문단의 마지막 사실로 끝낸다. 요약이나 교훈 문장을 덧붙이지 않는다.
- 이유와 과정은 문단으로 쓴다. 목록은 단계, 설정값, 병렬 항목을 나열할 때만 쓰고 본문의 15%를 넘기지 않는다. "**라벨**: 설명" 목록을 이어 쓰지 않는다. bold는 핵심 수치나 용어에만, 한 문단에 하나 이하로 쓴다.
- 나열은 자료에 있는 항목 수 그대로 쓴다. 항목 수를 셋으로 맞추지 않는다.
- 쉼표는 문장을 끊어 읽어야 할 때만 쓴다. 연결어미(~고, ~며, ~지만, ~는데) 뒤와 문장 첫머리의 접속부사(그리고, 하지만, 그래서, 따라서) 뒤에는 쉼표를 쓰지 않는다.
- "~하는 바입니다", "~하고자 합니다" 같은 합니다체 전용 관용구를 쓰지 않는다.
- 한글 표기가 굳어진 외래어(서버, 캐시)와 한국어로 굳어진 용어(어휘, 불용어, 학습, 추론)는 한글로 쓰고, 그 외 기술 용어는 영어 원문(race condition, latency, logit)으로 쓴다. 업계에서 쓰지 않는 번역어를 새로 만들지 않는다.

이 단계에서는 `references/ai-patterns.md`를 읽지 않는다. 피할 표현의 목록을 미리 보면 그 표현이 오히려 늘어날 수 있다.

### 5. 점검하고 고치기

1. 문체 검사를 실행한다(`--tone default`, `--facts`).
2. 문체 검사 결과의 GATE와 FAIL 항목은 반드시 고친다. WARN 항목은 deletion test로 지울 수 있는 문장이면 고치고, 아니면 둔다. WARN이 3개 이하면 통과다.
   - `references/ai-patterns.md`에서 그 항목을 고치는 방법을 찾는다.
   - 걸린 문장마다 deletion test를 한다. 그 구절을 지워도 정보(사실, 수치, 동작 원리)가 줄지 않으면 지우고, 정보가 있으면 그 정보를 직접 쓰는 문장으로 바꾼다. 주어, 목적어, 비교 기준, 수치가 가리키는 대상은 정보이므로 지우지 않는다.
   - 걸린 표현을 같은 수사 동작의 다른 표현으로 바꾸지 않는다. 예: "단순히 X가 아니라 Y"를 "X를 넘어 Y"로 바꾸는 것은 고친 것이 아니다.
   - 수치, 고유명사, 인용은 바꾸지 않는다. 자료가 추정한 내용을 단정으로 바꾸지 않는다.
   - 기준치 안으로 들어오면 멈춘다. 사람 글에도 있는 표현까지 0으로 만들지 않는다.
   - Edit 도구로 걸린 문장만 바꾼다.
3. 문체 검사를 다시 실행한다. 판정이 PASS가 될 때까지 최대 3회 반복한다. 고친 뒤 다른 항목의 수치가 늘었으면 그 수정을 다른 방법으로 고친다. `--all`을 붙이면 참고 지표(INFO)까지 볼 수 있다.
4. 단독 읽기 점검을 한다.
   - 점검할 문장은 문체 검사 결과의 "단독 읽기 점검 후보" 목록에 있는 문장, 절과 문단의 첫 문장, 수치가 든 문장이다.
   - 점검할 문장과 그 바로 앞 문장만 읽고, 이 문장이 무엇에 대한 말인지, 수치가 무엇을 잰 값이고 무엇과 비교한 값인지 답할 수 있으면 그대로 둔다.
   - 답할 수 없으면 빠진 주어, 측정 대상, 비교 기준을 fact sheet에서 찾아 그 문장에 채운다.
   - 같은 주어를 문장마다 되풀이하지 않는다. 새로 쓰는 주어는 기술, 설정, 지표의 이름으로 쓰고 "저자들은", "논문은", "원문은", "이 방식은"으로 채우지 않는다.
   - fact sheet 맨 위의 핵심 주제를 다시 읽고, 제목과 도입이 이 주제를 드러내는지, 각 절이 이 주제의 어느 부분을 설명하는지 확인한다. 핵심 주제를 설명하지 않는 세부는 지운다.
5. 수치, 인과, 범위를 말하는 문장을 fact sheet와 하나씩 대조한다. 4단계에서 채운 주어와 측정 대상도 대조한다.
   - 수치: 값, 단위, 비교 기준("~의 20%"와 "~보다 20%"), 조건이 원문 표현과 같은가
   - 인과: "~때문에", "~해서 ~한다"는 자료가 설명한 원인인가. 자료에 없는 원인이면 추론임을 드러내거나("~일 수 있습니다") 지운다.
   - 범위와 빈도: "모두", "~뿐", "항상", "자주", "몇 문단마다"가 자료의 표현인가
   - 일반화: "~할수록 ~하다", "~하면 ~한다" 같은 법칙 문장이 자료에 있는가. 자료가 예시 하나만 들었으면 그 예시로 다시 쓰거나 추론임을 드러낸다.
   - 방법의 세부: 토큰화 방식, 단위, 설정값처럼 방법을 설명하는 세부가 자료에 있는가. 자료에 없는 세부를 덧붙이지 않는다.
   - 도입 장면과 적용 절: 두 곳은 자료의 문장을 옮기지 않고 풀어 쓰는 곳이라 빈도와 일반화가 덧붙기 쉽다. 적용 절에서 자료에 없는 내용은 조건("~라면")이나 가능성("~수 있습니다")으로 쓰였는지 본다.
6. `references/rubric.md`의 판정 항목 J1~J9로 글을 직접 읽고 점검한다. 특히 J1(자료의 문제, 방법, 결과, 한계가 다 있는가), J3(지워도 되는 문장이 없는가), J5(한국 개발자가 쓴 글처럼 읽히는가), J9(문장을 따로 읽어도 무엇에 대한 말인지 알 수 있는가)를 본다.

### 6. 후처리

초안은 모든 글에 같은 규칙을 적용해서 썼다. 후처리는 초안을 이 글의 독자 입장에서 처음부터 다시 읽고, 이 글에 필요 없는 반복과 이 글에 필요한데 빠진 정보를 고친다. 일반 규칙이나 lint 기준치와 다른 형태라도 이 글의 독자에게 더 읽기 쉬우면 그 형태를 쓴다.

1. `references/revision.md`를 읽는다.
2. 후처리 시작 명령(`revise_ko.py start`)으로 후처리 전 초안 사본을 만든다.
3. 후처리 대상을 Read로 처음부터 끝까지 읽고, 독자가 읽다가 멈출 곳을 줄 번호와 이유와 함께 적는다. 다 읽은 뒤 `revise_ko.py repeats`의 반복 후보를 revision.md의 판단 질문으로 판단한다.
4. 적은 곳만 Edit 도구로 고친다. 글쓴이가 계산한 값과 고친 수치 문장은 자료 원문으로 다시 확인한다.
5. `revise_ko.py check`를 실행하고, 종료 코드가 0이 될 때까지 걸린 항목을 revision.md의 "고친 뒤 확인"대로 처리한다.
- Bash를 쓸 수 없으면 사본 없이 고치고 revision.md의 "스크립트를 쓸 수 없을 때"를 따른다.

### 7. 어투 적용 (Casual일 때, `--retone`일 때)

1. `references/tone.md`를 읽는다.
2. 후처리를 마친 Default 초안의 문장마다 종결부(마지막 1~2 어절)만 바꿔 출력 파일에 쓴다. 어투를 바꿀 때 문장의 내용, 주어, 수치는 고치지 않는다. 문장을 나누거나 합치지 않는다. 헤딩, 코드, 표, 인용, 명사구 목록은 그대로 둔다.
3. 어투 검사를 실행한다. 인자 순서는 항상 Default 글, Casual 글이다. FAIL이 나온 문장은 종결부만 다시 고친다.
4. 출력 파일에 문체 검사를 `--tone casual`로 실행한다. 종결어미 항목(G4, T.*)이 걸리면 출력 파일에서 고친다. 그 밖의 항목이 걸리면 Default 초안(`<이름>.draft.md`)의 해당 문장을 고치고 그 문장을 다시 변환한다.
- `--retone`이면 입력 파일이 Default 초안이다. Casual 글을 Default로 바꿀 때도 같은 대응표를 반대로 쓰고, 어투 검사의 인자 순서는 Default 글, Casual 글로 둔다.

### 8. 정리하고 보고하기

- `--keep-work`가 없으면 작업 파일 삭제 명령을 실행한다.
- 사용자에게 짧게 보고한다. 보고에는 저장 경로, 어투, 본문 글자 수, 초안과 최종 글의 문체 검사 판정(Gate, FAIL, WARN 수), 후처리에서 고친 문장 수, 남긴 WARN과 남긴 이유, 어투 검사 결과(Casual일 때), 사용한 자료를 쓴다. 글 본문을 대화에 다시 붙이지 않는다.
- 최종 글의 조건은 Gate 위반 0, FAIL 0, 후처리로 나빠진 AI 문체 항목 0이다. 문장·문단 분포 항목(A8, A9, A16, A17)의 WARN은 후처리에서 의도한 형태면 남길 수 있어서, 최종 글의 WARN은 3개를 넘을 수 있다.

## 참고 문서

- `references/style-guide.md`는 글 골격, 문장과 문단, 용어와 수치 표기를 다룬다. 3단계에서 읽는다.
- `references/ai-patterns.md`는 AI 문체 패턴과 고치는 방법을 다룬다. 5단계에서 읽는다.
- `references/rubric.md`는 평가 기준과 근거 자료를 다룬다. 5단계에서 읽는다.
- `references/revision.md`는 후처리의 판단 질문, 고칠 곳과 고치는 방법, 수치 재확인 방법을 다룬다. 6단계에서 읽는다.
- `references/tone.md`는 Default와 Casual의 종결어미 대응표다. 7단계에서 읽는다.
