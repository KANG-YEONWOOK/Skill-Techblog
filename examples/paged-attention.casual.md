# PagedAttention: KV cache를 페이지처럼 나눠 LLM 서빙 처리량을 2~4배 높인 방법

ChatGPT 같은 챗봇에 질문을 보내면 답이 한꺼번에 뜨지 않고 몇 글자씩 이어서 나타나요. 챗봇 뒤에서 동작하는 LLM(대규모 언어 모델)은 실제로 답을 토큰 단위로 하나씩 만들어요. LLM은 많은 텍스트로 학습해 주어진 텍스트 뒤에 올 토큰을 하나씩 이어 붙이는 모델이고, 토큰은 모델이 텍스트를 나눠 처리하는 단위로 낱말이나 낱말 조각 하나에 해당해요.

LLM을 실행하는 장치는 많은 계산을 동시에 처리하는 칩인 GPU(그래픽 처리 장치)예요. 새 토큰을 만들 때마다 모델은 앞 토큰 전부를 다시 참고하므로 앞 토큰마다 계산한 결과를 GPU에 붙은 메모리(GPU 메모리)에 저장해 두고 꺼내 사용해요.

이렇게 저장한 데이터를 KV cache라고 불러요. KV는 저장하는 결과가 토큰마다 계산한 key 벡터와 value 벡터 두 가지라는 뜻이고, 벡터는 숫자 여러 개를 한 줄로 늘어놓은 값이에요. 새 토큰을 만들 때 모델은 앞 토큰의 key 벡터로 그 토큰을 얼마나 참고할지 정하고, value 벡터에서 그 토큰이 넘겨줄 정보를 가져와요. 캐시는 같은 계산을 다시 하지 않으려고 결과를 저장해 두는 곳이에요.

학습을 마친 모델을 서버에서 실행해 사용자 요청에 답을 돌려주는 일을 서빙이라고 불러요. KV cache는 요청마다 따로 생기고 답이 길어질수록 커지는데, 답이 얼마나 길어질지는 미리 알 수 없어요. 그래서 기존 서빙 시스템은 요청마다 최대 길이만큼 메모리를 미리 잡아 둬요.

최대 길이를 2048 토큰으로 잡은 요청이 프롬프트(사용자가 모델에 보낸 입력 텍스트) 7개 토큰과 출력 3개 토큰으로 끝나면 미리 잡은 슬롯 2048개 가운데 2038개는 한 번도 사용되지 않아요. 슬롯은 토큰 하나의 KV cache가 들어가는 메모리 단위예요.

PagedAttention은 미리 잡아 두고 사용하지 않는 KV cache 메모리를 줄이려고 만든 attention 알고리즘이에요. attention은 LLM이 새 토큰을 만들 때 앞 토큰들을 각각 얼마나 참고할지 계산하는 연산이고, 이름은 '주의'라는 뜻이에요. KV cache는 이 연산에 사용하는 데이터예요. PagedAttention은 운영체제가 메모리를 같은 크기의 페이지로 나눠 관리하는 페이징을 본떠 KV cache를 같은 크기의 블록으로 나눠요. 블록들을 GPU 메모리의 떨어진 위치에 저장해도 attention을 계산할 수 있고, 이름도 페이징을 적용한(paged) attention이라는 뜻이에요.

vLLM은 PagedAttention 위에 만든 LLM 서빙 시스템이에요. KV cache를 블록 단위로 관리하고 한 요청의 여러 출력이나 여러 요청이 같은 블록을 공유하게 해요.

미국 대학인 UC Berkeley 등의 연구진은 2023년 운영체제 분야 학회인 SOSP(Symposium on Operating Systems Principles)에서 발표한 논문 "Efficient Memory Management for Large Language Model Serving with PagedAttention"으로 두 기술을 제안했어요. 아래에서는 이 논문을 Kwon 등(2023)이라고 불러요.

이 글에서는 KV cache 메모리가 어디서 낭비되고 PagedAttention이 그 낭비를 어떻게 줄이는지 정리해요. 논문의 실험에서 vLLM은 지연 시간(요청을 보낸 뒤 응답을 받을 때까지 걸리는 시간)을 같은 수준으로 유지하면서 기존 서빙 시스템인 FasterTransformer와 Orca보다 처리량을 2~4배 높였어요. 처리량은 1초에 처리하는 토큰 수나 요청 수예요. FasterTransformer는 NVIDIA가 지연 시간을 줄이는 쪽으로 최적화한 LLM 추론 엔진(학습을 마친 모델을 실행하는 소프트웨어)이고, Orca는 처리량을 높이는 쪽으로 최적화한 LLM 서빙 시스템이에요.

## LLM 서빙에서 GPU 메모리가 처리량을 정하는 이유

Kwon 등(2023)이 인용한 Reuters 기사의 추정으로는 LLM 요청 하나를 처리하는 비용이 기존 키워드 검색 한 번의 10배에 이를 수 있어요. 요청 하나에 드는 비용을 낮추려면 같은 GPU로 처리하는 요청 수, 곧 처리량을 높여야 해요.

### 토큰을 하나씩 만드는 두 단계

LLM 서비스에 들어온 요청은 프롬프트를 담고 있고 모델은 프롬프트 뒤에 출력 토큰을 하나씩 이어 붙여요. 프롬프트와 출력을 이어 붙인 토큰 목록은 시퀀스라고 불러요.

출력 토큰을 만들 때 attention은 지금 만들 토큰 쪽에서 계산한 query 벡터와 앞 토큰들의 key 벡터를 곱해 앞 토큰마다 점수를 매겨요. 이 점수가 높은 토큰일수록 그 토큰의 value 벡터를 크게 반영해 앞 토큰들의 value 벡터를 평균해요. key 벡터는 그 토큰을 얼마나 참고할지 정하는 데 사용하고 value 벡터는 그 토큰이 넘겨줄 정보를 담아요. query, key, value는 각각 '질의', '열쇠', '값'이라는 뜻으로, query와 잘 맞는 key일수록 그 key에 딸린 value를 많이 가져오는 attention의 계산을 나타내요.

프롬프트 단계는 프롬프트 토큰 전체를 한 번에 계산해 첫 출력 토큰과 프롬프트의 KV cache를 만드는 단계예요. 프롬프트 토큰은 처음부터 모두 주어져 있어서 이 계산은 GPU에서 병렬로 처리돼요.

생성 단계는 남은 출력 토큰을 반복(iteration)마다 하나씩 만드는 단계예요. 반복마다 새 토큰 하나의 key 벡터와 value 벡터만 계산하고 앞 토큰들의 벡터는 KV cache에서 꺼내 사용해요.

각 반복은 앞 반복이 만든 토큰이 있어야 시작할 수 있어 병렬로 처리할 수 없어요. 그래서 생성 단계는 GPU의 연산 능력을 다 사용하지 못하고 요청 하나의 지연 시간 대부분을 차지해요.

### 여러 요청을 묶어 계산하는 배치

GPU의 남는 연산 능력은 여러 요청을 배치로 묶어 함께 계산하면 활용할 수 있어요. 배치는 GPU가 한 번에 계산하는 요청 묶음이고, 묶은 요청 수를 배치 크기라고 불러요. 배치 안의 요청들은 모델의 파라미터(모델이 학습으로 정해 둔 숫자 값들)를 함께 사용해서 파라미터를 옮기는 비용이 요청 수만큼 나뉘어요.

Orca는 배치를 반복 단위로 관리하고 처리량을 높이도록 최적화한 LLM 서빙 시스템이에요. Orca가 사용하는 iteration-level scheduling은 반복이 끝날 때마다 다 끝난 요청을 배치에서 빼고 새 요청을 넣어요. 그래서 새 요청은 배치 전체가 끝나기를 기다리지 않고 반복 한 번만 기다리면 돼요.

### KV cache가 차지하는 메모리

요청을 유연하게 묶어도 배치에 넣을 수 있는 요청 수는 KV cache에 할당한 GPU 메모리가 정해요. 메모리 할당은 프로그램이 사용할 메모리 영역을 정해 내주는 일이에요.

공개 LLM인 OPT의 파라미터 130억 개짜리 모델(OPT-13B)에서 토큰 하나의 KV cache는 800KB예요. key와 value 두 벡터, 토큰 하나를 나타내는 벡터의 길이 5120, 층 40개, 숫자 하나당 2바이트를 모두 곱한 값이에요. 층은 모델이 같은 구조의 계산을 여러 겹 쌓았을 때 그 한 겹을 말해요.

OPT는 시퀀스를 최대 2048 토큰까지 만들 수 있으므로 요청 하나의 KV cache는 1.6GB까지 커질 수 있어요.

파라미터 130억 개짜리 LLM을 NVIDIA의 데이터센터용 GPU인 A100(메모리 40GB)에서 서빙하면 메모리의 약 65%인 26GB를 파라미터가 서빙 내내 차지해요. 30% 가까이는 요청마다 생겼다 사라지는 KV cache가 사용하고 나머지 적은 양은 계산 중에 잠깐 만들었다 버리는 중간 값이 차지해요.

파라미터가 차지하는 양은 고정되어 있으므로 배치 크기의 상한은 KV cache를 얼마나 효율적으로 관리하느냐에 달려 있어요.

## 기존 시스템은 KV cache 메모리를 얼마나 낭비했을까

FasterTransformer와 Orca 같은 기존 서빙 시스템은 요청 하나의 KV cache를 연속된 메모리 공간, 곧 주소(메모리 위치마다 붙은 번호)가 끊기지 않고 이어진 영역에 저장해요. AI 모델을 만들고 실행하는 데 사용하는 소프트웨어인 딥러닝 프레임워크 대부분이 데이터를 연속된 메모리에 저장하도록 요구하거든요. 출력 길이는 미리 알 수 없으므로 이 시스템들은 요청의 최대 길이만큼 공간을 미리 할당해요.

미리 할당한 공간 가운데 앞으로 만들 토큰을 위해 잡아 둔 슬롯을 예약 공간이라고 불러요. 예약 공간은 결국 사용되지만 요청이 끝날 때까지 다른 요청이 사용할 수 없어요.

최대 길이만큼 잡았는데 출력이 일찍 끝나서 끝까지 비어 있는 슬롯은 내부 단편화라고 불러요.

요청마다 잡는 크기가 달라 할당한 공간들 사이에 남은 작은 빈 공간은 다른 요청을 담기에 작아서 사용할 수 없고, 이 낭비가 외부 단편화예요.

### Orca 세 버전의 메모리 사용

Orca는 공개되지 않아서 Kwon 등(2023)은 Orca를 직접 구현하고 출력 공간을 얼마나 잡는지에 따라 세 버전으로 나눴어요. 세 버전 모두 메모리 주소를 buddy allocator로 정한다고 가정했고, buddy allocator는 요청한 크기를 2의 거듭제곱으로 올려 메모리를 나눠 주는 할당 방식이에요. 이름의 buddy는 '짝'이라는 뜻으로, 메모리 덩어리를 반으로 나눈 두 조각을 서로의 짝으로 관리하는 데서 왔어요.

- Orca (Oracle)는 요청이 실제로 만들 출력 길이를 미리 안다고 가정한 버전으로, 실제로는 만들 수 없는 성능 상한이에요. Oracle은 '앞일을 알려 주는 신탁'이라는 뜻이에요.
- Orca (Pow2)는 출력 공간을 실제 출력 길이의 2배 안에서 2의 거듭제곱(power of 2)으로 잡아요. 실제 출력이 25 토큰이면 32 토큰을 잡아요.
- Orca (Max)는 늘 모델의 최대 시퀀스 길이인 2048 토큰까지 잡아요.

아래 표는 요청 하나가 출력 하나를 만드는 실험에서 KV cache 메모리를 어디에 사용했는지 평균 비율로 나타내요.

| 시스템 | 실제 토큰 저장 | 예약 공간 | 내부 단편화 | 외부 단편화와 기타 |
|---|---|---|---|---|
| Orca (Max) | 20.4% | 13.3% | 57.3% | 8.9% |
| Orca (Pow2) | 26.8% | 17.9% | 13.6% | 41.6% |
| Orca (Oracle) | 38.2% | 25.2% | - | 36.6% |
| vLLM | 96.3% | - | - | - |

Orca 세 버전에서 실제 토큰의 KV cache를 저장한 메모리는 20.4~38.2%였어요.

출력 길이를 정확히 아는 Orca (Oracle)도 38.2%에 그쳤는데, 예약 공간이 25.2%, 외부 단편화와 기타가 36.6%를 차지했기 때문이에요. Orca (Pow2)는 Orca (Max)보다 내부 단편화를 57.3%에서 13.6%로 줄였지만 외부 단편화와 기타는 8.9%에서 41.6%로 늘었어요.

vLLM은 같은 실험에서 KV cache 메모리의 96.3%를 실제 토큰 저장에 사용했어요.

### 공유할 수 없는 KV cache

디코딩 방식은 모델이 계산한 다음 토큰 확률로 실제 출력 토큰을 고르는 방법이에요. 디코딩은 '부호를 푼다'는 뜻의 낱말로, 언어 모델에서는 모델이 출력 텍스트를 만들어 내는 과정을 가리켜요. 요청 하나로 출력 시퀀스 여러 개를 만드는 디코딩 방식에서는 시퀀스들이 프롬프트의 KV cache를 함께 사용할 수 있지만, 기존 시스템은 시퀀스마다 별도의 연속된 공간에 KV cache를 저장해서 공유하지 못해요.

## 운영체제의 페이징을 KV cache에 적용하기

### 가상 메모리와 페이징

운영체제의 가상 메모리는 프로그램에 연속된 메모리처럼 보이는 주소 공간을 주고, 실제로는 물리 메모리(컴퓨터에 실제로 달린 메모리)의 흩어진 조각에 연결해 주는 기능이에요.

페이징은 이 연결을 고정 크기 단위로 처리하는 방식이에요. 운영체제는 메모리를 같은 크기의 페이지로 나누고 프로그램이 보는 논리 페이지를 물리 메모리의 물리 페이지에 연결해요. 논리 페이지가 이어져 있어도 물리 페이지는 흩어져 있을 수 있고, 물리 페이지를 미리 다 잡아 두지 않고 필요할 때 할당할 수 있어요.

PagedAttention에서는 블록이 페이지에, 토큰이 바이트에, 요청이 프로세스(실행 중인 프로그램)에 해당해요. 페이지 하나에 바이트 여러 개가 담기듯 블록 하나에는 토큰 여러 개의 KV cache가 담기고, 운영체제가 프로세스마다 페이지를 연결하듯 vLLM은 요청마다 블록을 연결해요.

### 블록과 block table

PagedAttention은 시퀀스마다 KV cache를 블록으로 나눠요. 블록 하나에는 정해진 수의 토큰의 key 벡터와 value 벡터가 들어가고, 이 토큰 수를 블록 크기라고 불러요.

vLLM의 기본 블록 크기는 16이에요.

PagedAttention의 GPU 커널은 블록을 하나씩 찾아 가져와 query 벡터와 블록 안의 key 벡터들을 곱해 점수를 구하고, 그 점수를 블록의 value 벡터들에 곱해요. GPU 커널은 GPU에서 실행되는 작은 프로그램 하나예요. 이렇게 블록 단위로 계산하므로 블록들은 GPU 메모리에서 서로 떨어져 있어도 돼요.

요청 쪽에서 순서대로 보는 블록을 논리 블록, GPU 메모리에 실제로 잡힌 블록을 물리 블록이라고 불러요. 요청의 KV cache는 논리 블록 0, 1, 2 순서로 앞에서부터 채워져요.

요청마다 하나씩 있는 block table은 논리 블록마다 연결된 물리 블록 번호와 그 블록에 찬 토큰 수를 기록한 표예요. 논리 블록과 물리 블록을 분리한 덕분에 vLLM은 슬롯을 미리 다 잡지 않고도 KV cache를 늘려 갈 수 있어요.

### 토큰 7개짜리 프롬프트가 블록을 채우는 순서

Kwon 등(2023)의 예에서 블록 크기는 4이고 요청의 프롬프트 "Four score and seven years ago our"는 토큰 7개예요.

1. 프롬프트 단계에서 vLLM은 논리 블록 0과 1을 물리 블록 7과 1에 연결해요. 처음 토큰 4개의 KV cache는 논리 블록 0에, 다음 3개는 논리 블록 1에 저장하고 논리 블록 1의 남은 슬롯 하나는 생성 단계를 위해 비워 둬요.
2. 첫 생성 단계에서 만든 토큰 "fathers"의 KV cache는 논리 블록 1의 빈 슬롯에 들어가요. block table에 기록한 논리 블록 1의 토큰 수는 3에서 4로 바뀌어요.
3. 둘째 생성 단계에서는 논리 블록 1이 가득 찼으므로 vLLM이 논리 블록 2를 새로 만들고 물리 블록 3을 할당해 block table에 기록해요.

vLLM은 앞 블록이 가득 찬 뒤에만 새 물리 블록을 할당하므로 요청 하나가 낭비하는 공간은 마지막 블록의 빈 슬롯뿐이에요. 기본 블록 크기 16에서 요청 하나가 비워 두는 슬롯은 많아야 15개예요.

요청이 끝나면 vLLM은 그 요청의 블록을 해제해 다른 요청의 KV cache를 저장해요.

## 블록을 공유하는 디코딩 방식

모델이 계산한 확률로 출력 토큰을 고르는 디코딩 방식에는 프롬프트 하나로 출력 시퀀스 하나를 만드는 방식도 있고, 요청 하나로 시퀀스 여러 개를 만드는 방식도 있어요. 시퀀스 여러 개를 만드는 방식에서는 vLLM이 시퀀스들 사이에서 물리 블록을 공유해요.

vLLM은 이런 디코딩 방식을 `fork`, `append`, `free` 세 연산으로 구현해요. `fork`는 기존 시퀀스에서 새 시퀀스를 갈라 만들고, `append`는 시퀀스 끝에 새 토큰을 붙이고, `free`는 시퀀스를 지워요. 모델과 GPU 커널은 시퀀스마다 물리 블록 번호 목록만 받으므로 디코딩 방식이 다른 요청도 한 배치에 함께 넣을 수 있어요.

### parallel sampling과 copy-on-write

parallel sampling은 프롬프트 하나로 출력을 여러 개 만들어 사용자가 그중 하나를 고르게 하는 디코딩 방식이고 코드 작성 도우미에서 사용해요. 이름은 확률에 따라 토큰을 뽑는 일(sampling)을 여러 출력에서 나란히(parallel) 한다는 뜻이에요. 출력들이 같은 프롬프트를 공유하므로 vLLM은 프롬프트의 KV cache를 한 벌만 저장해요. Kwon 등(2023)의 예에서 두 출력 A1과 A2의 논리 블록 0과 1은 모두 물리 블록 7과 1에 연결돼요.

물리 블록 하나를 여러 논리 블록이 가리킬 수 있어서 vLLM은 물리 블록마다 reference count, 곧 그 물리 블록을 가리키는 논리 블록 수를 관리해요. A1과 A2가 프롬프트를 공유하는 이 예에서 물리 블록 7과 1의 reference count는 2예요.

생성 단계에서 A1과 A2는 서로 다른 토큰을 만들기 때문에 KV cache를 따로 저장해야 해요. A1이 마지막 논리 블록에 새 KV cache를 저장하려 하면 vLLM은 물리 블록 1의 reference count가 1보다 큰 것을 확인하고, 새 물리 블록 3을 할당해 내용을 복사한 뒤 물리 블록 1의 reference count를 1로 줄여요. 이어서 A2는 reference count가 이미 1인 물리 블록 1에 바로 저장해요.

이 방식은 운영체제의 copy-on-write를 블록 단위로 옮긴 거예요. copy-on-write는 여러 쪽이 데이터 하나를 공유하다가 한쪽이 그 데이터를 수정하려 할 때만 복사본을 만드는 기법이고, 이름은 '기록할 때 복사한다'는 뜻이에요.

### beam search

beam search는 단계마다 확률이 높은 후보 시퀀스를 정해진 수만 남기며 이어 가서 가장 그럴듯한 출력을 찾는 디코딩 방식이고 기계 번역에서 사용해요. 단계마다 남기는 후보 수를 beam width라고 불러요. beam은 '빛줄기'라는 뜻이고, beam width는 손전등 빛줄기의 폭을 넓히거나 좁히듯 남길 후보 수를 정한다는 비유에서 나온 이름이에요.

beam search의 후보들은 프롬프트 블록뿐 아니라 서로 갈라지기 전에 함께 만든 출력 토큰의 블록도 공유하고, 공유 관계는 디코딩이 진행되면서 바뀌어요. 상위 후보에서 밀려난 후보의 논리 블록은 해제되고 reference count가 0이 된 물리 블록도 해제돼요.

기존 시스템은 후보 사이에서 KV cache를 자주 복사해야 했어요. vLLM에서는 대부분의 블록을 공유하고 새 토큰이 공유 중인 블록에 들어갈 때만 copy-on-write로 블록 하나를 복사해요.

### 시스템 프롬프트를 공유하는 shared prefix

LLM을 사용하는 쪽은 흔히 작업 지시와 입력, 출력 예시를 담은 긴 설명을 실제 작업 입력 앞에 붙여 프롬프트를 만들고, 이 설명을 시스템 프롬프트라고 불러요. 여러 요청의 프롬프트 앞부분에 똑같이 들어가는 이런 지시문과 예시가 shared prefix예요.

vLLM에서는 서비스 제공자가 shared prefix의 KV cache를 물리 블록에 미리 저장해 둬요. 같은 shared prefix로 시작하는 요청은 논리 블록을 그 물리 블록에 연결하고 마지막 블록만 copy-on-write로 표시하므로 프롬프트 단계의 계산은 작업 입력 부분에만 실행해요.

## GPU 메모리가 모자랄 때의 선점, 스와핑, 재계산

요청이 늘고 출력이 길어지면 새 KV cache를 저장할 물리 블록이 바닥날 수 있어요. vLLM은 FCFS(first-come-first-serve) 정책에 따라 먼저 도착한 요청을 먼저 처리하고, 요청을 선점해야 하면 가장 늦게 도착한 요청부터 선점해요. 선점은 처리 중인 요청을 잠시 멈추고 그 요청이 사용하던 메모리를 다른 요청에 내주는 일이에요.

블록을 내보낼 때는 all-or-nothing 정책을 따라요. 한 시퀀스의 블록은 attention 계산에서 늘 함께 사용되므로 시퀀스의 블록을 모두 내보내거나 하나도 내보내지 않아요. 정책 이름도 '전부 아니면 하나도 아님'이라는 뜻이에요.

스와핑은 내보낸 블록을 CPU 메모리로 복사해 두었다가 다시 GPU 메모리로 가져오는 방법이에요. swap은 '맞바꾸다'라는 뜻이고, 운영체제의 가상 메모리가 내보낸 페이지를 디스크에 복사해 두는 기법도 같은 이름으로 불러요. CPU 메모리는 GPU가 아닌 CPU(중앙 처리 장치) 쪽 메모리예요.

재계산은 내보낸 KV cache를 버렸다가 요청을 다시 처리할 때 새로 계산하는 방법이에요. 그동안 만든 출력 토큰을 원래 프롬프트에 이어 붙여 새 프롬프트로 처리하면 모든 위치의 KV cache를 프롬프트 단계 한 번으로 만들 수 있어요.

그래서 재계산에 걸리는 시간은 처음 생성할 때 걸린 시간보다 훨씬 짧을 수 있어요.

## 같은 지연 시간에서 요청을 몇 배 더 처리했을까

### 실험에 사용한 모델과 비교 대상

실험에는 OPT의 파라미터 130억, 660억, 1750억 개 모델(각각 OPT-13B, OPT-66B, OPT-175B)과 공개 LLM인 LLaMA의 파라미터 130억 개 모델(LLaMA-13B)을 사용했어요. GPU는 Google이 서버를 빌려주는 클라우드 서비스인 Google Cloud의 NVIDIA A100이고, OPT-175B에는 메모리가 80GB인 A100(A100-80GB)을 사용했어요. 모델 크기별 서버 구성은 아래와 같고, 표의 K는 천을 뜻해요.

| 모델 | GPU | 전체 GPU 메모리 | 파라미터 크기 | KV cache용 메모리 | KV cache 최대 슬롯 수 |
|---|---|---|---|---|---|
| OPT-13B | A100 1개 | 40GB | 26GB | 12GB | 15.7K |
| OPT-66B | A100 4개 | 160GB | 132GB | 21GB | 9.7K |
| OPT-175B | A100-80GB 8개 | 640GB | 346GB | 264GB | 60.1K |

OPT-66B는 KV cache용 메모리가 21GB로 OPT-13B보다 많지만 KV cache 슬롯은 9.7K개로 OPT-13B의 15.7K개보다 적어요. KV cache용 메모리를 슬롯 수로 나누면 슬롯 하나의 크기는 OPT-13B가 약 0.8MB, OPT-66B가 약 2.2MB예요.

실험 요청은 두 데이터셋(실험에 사용하는 데이터 모음)의 입력과 출력 길이를 따라 만들었어요. ShareGPT는 사용자들이 공유한 ChatGPT 대화를 모은 데이터셋이에요. Alpaca는 OpenAI의 LLM인 GPT-3.5로 만든 지시문 데이터셋으로, 지시문과 그 답을 모았어요.

ShareGPT의 평균 길이는 입력 161.31 토큰, 출력 337.99 토큰으로 Alpaca(입력 19.31 토큰, 출력 58.45 토큰)보다 입력이 8.4배, 출력이 5.8배 길어요.

두 데이터셋에는 요청 도착 시각이 없어서 요청 빈도(1초에 들어오는 요청 수)를 바꿔 가며 도착 시각을 무작위로 만들었어요.

비교 대상은 FasterTransformer와 Orca 세 버전이에요. FasterTransformer는 NVIDIA가 만든 LLM 추론 엔진(학습을 마친 모델을 실행하는 소프트웨어)으로 지연 시간을 줄이는 쪽으로 최적화되어 있어요. Orca (Oracle)는 실제 출력 길이만큼, Orca (Pow2)는 그 2배 안에서 2의 거듭제곱으로, Orca (Max)는 늘 2048 토큰으로 출력 공간을 잡아요.

성능은 normalized latency로 측정했어요. normalized latency는 요청마다 전체 지연 시간을 출력 토큰 수로 나눈 값의 평균이고, 이름은 지연 시간을 출력 토큰 하나당 값으로 맞췄다(normalized)는 뜻이에요. 처리량이 높은 시스템은 요청 빈도가 높아져도 이 값을 낮게 유지해요.

### 요청 하나가 출력 하나를 만들 때

요청 빈도를 높이면 normalized latency는 처음에는 천천히 늘다가 요청 빈도가 시스템이 처리할 수 있는 양을 넘는 지점에서 갑자기 치솟아요. 이 지점을 넘으면 대기열이 끝없이 길어지거든요.

ShareGPT에서 vLLM은 비슷한 지연 시간을 유지하면서 Orca (Oracle)보다 1.7~2.7배, Orca (Max)보다 2.7~8배 높은 요청 빈도를 감당했어요. vLLM이 감당한 요청 빈도는 FasterTransformer의 최대 22배였어요.

vLLM이 더 높은 요청 빈도를 감당한 이유는 배치에 함께 넣은 요청 수에서 드러나요. 아래 표는 OPT-13B를 서빙할 때 배치에 평균적으로 함께 넣은 요청 수예요.

| 데이터셋(요청 빈도) | Orca (Max) | Orca (Pow2) | Orca (Oracle) | vLLM |
|---|---|---|---|---|
| ShareGPT(초당 2개) | 7.00 | 9.81 | 13.62 | 30.42 |
| Alpaca(초당 30개) | 7.00 | 43.24 | 72.75 | 132.44 |

ShareGPT에서 vLLM은 Orca (Oracle)보다 2.2배, Orca (Max)보다 4.3배 많은 요청을 함께 처리했어요.

Orca (Max)는 두 데이터셋에서 모두 7.00개를 묶었어요. OPT-13B의 KV cache 슬롯 15.7K개를 요청당 2048 슬롯으로 나누면 7.7이라서 Orca (Max)에는 요청이 7개까지만 들어가요. 요청이 짧은 Alpaca에서도 Orca (Max)는 요청마다 2048 슬롯을 잡아서 vLLM과의 차이가 132.44개와 7.00개, 약 18.9배로 벌어졌어요.

Alpaca로 OPT-175B를 서빙한 실험에서는 vLLM이 Orca (Oracle)와 Orca (Pow2)보다 앞선 폭이 작았어요. OPT-175B 서버는 KV cache에 264GB를 할당할 수 있고 Alpaca 요청은 짧아서 Orca도 요청을 많이 묶을 수 있었어요. 이 조건에서는 성능의 상한을 GPU 메모리가 아니라 GPU의 연산 능력이 정했어요.

### 출력 여러 개를 만드는 요청과 shared prefix, 챗봇

출력 시퀀스 수나 beam width가 클수록 vLLM과 Orca 세 버전이 감당한 요청 빈도의 차이가 커졌어요. OPT-13B와 Alpaca 조건에서 vLLM이 감당한 요청 빈도는 출력 하나를 만드는 경우 Orca (Oracle)의 1.3배였고, beam width가 6인 beam search에서는 2.3배였어요.

아래 표는 같은 조건에서 블록 공유로 아낀 메모리의 비율이에요. 공유로 아낀 블록 수를 공유하지 않았을 때의 전체 블록 수로 나눈 값이에요.

| 디코딩 방식(OPT-13B, Alpaca) | 2 | 4 | 6 |
|---|---|---|---|
| parallel sampling(출력 시퀀스 수) | 6.09% | 8.53% | 9.79% |
| beam search(beam width) | 37.56% | 53.13% | 55.16% |

ShareGPT에서는 parallel sampling이 16.2~30.5%, beam search가 44.3~66.3%를 아꼈어요. 프롬프트만 공유하는 parallel sampling은 프롬프트가 평균 161.31 토큰인 ShareGPT에서 평균 19.31 토큰인 Alpaca보다 메모리를 더 많이 아꼈어요.

shared prefix 실험에는 여러 언어를 다루는 LLaMA-13B와 WMT16 영어-독일어 번역 데이터를 사용했어요. WMT16은 2016년 기계 번역 학회(Conference on Machine Translation)가 공개한 번역 데이터셋이에요. 번역 예시 1개를 담은 80 토큰짜리 shared prefix에서 vLLM의 처리량은 Orca (Oracle)의 1.67배였고, 예시 5개를 담은 341 토큰짜리 shared prefix에서는 3.58배였어요.

챗봇 실험에서는 ShareGPT 대화의 기록과 마지막 질문을 이어 붙인 프롬프트를 마지막 1024 토큰으로 자르고 출력은 최대 1024 토큰까지 만들었어요. 이 실험에서 vLLM은 Orca 세 버전보다 2배 높은 요청 빈도를 감당했어요. 대부분의 프롬프트가 1024 토큰이었고 Orca 세 버전은 buddy allocator 때문에 출력 길이 예측과 상관없이 출력용으로 1024 토큰 공간을 잡았어요. 그래서 Orca 세 버전의 결과는 서로 비슷했어요. 반면 vLLM은 PagedAttention으로 단편화와 예약 공간 문제를 줄여 긴 프롬프트도 효율적으로 처리했어요.

### 블록 크기와 GPU 커널의 오버헤드

PagedAttention의 attention 커널은 block table을 읽고 조건 검사를 더 실행하는 오버헤드 때문에 FasterTransformer의 커널보다 지연 시간이 20~26% 길었어요. 오버헤드는 본래 작업 외에 추가로 드는 시간이나 자원이에요. Kwon 등(2023)은 이 오버헤드가 attention 연산에만 생기므로 작다고 판단해요.

블록 크기는 ShareGPT에서 16~128일 때 성능이 가장 좋았어요. Alpaca에서는 16과 32가 좋았고, 그보다 큰 블록은 시퀀스가 블록보다 짧아지면서 성능을 크게 떨어뜨렸어요.

블록 크기 16은 대부분의 조건에서 GPU를 효율적으로 활용할 만큼 크고 내부 단편화가 크게 생기지 않을 만큼 작아서 vLLM의 기본값이 되었어요.

스와핑은 블록이 작을 때 CPU와 GPU 사이에 작은 전송이 많아져 오버헤드가 컸고, 재계산은 블록 크기와 상관없이 오버헤드가 일정했어요. 블록 크기 16~64에서는 두 방법의 전체 성능이 비슷했어요.

## 한국어 서비스에 적용한다면

Kwon 등(2023)의 실험에서 vLLM의 개선 폭은 시퀀스가 길수록 컸어요. 한국어 서비스라면 토크나이저(텍스트를 토큰으로 나누는 프로그램)에 따라 한 낱말이 여러 토큰으로 나뉘어 같은 내용을 영어로 쓸 때보다 시퀀스가 길어질 수 있어요.

이 경우 vLLM의 이점이 논문의 실험에서보다 클 수 있지만, 실험 데이터에는 한국어 요청만 모은 데이터셋이 없었으므로 자기 서비스의 토큰 길이 분포로 직접 측정해야 해요.

모든 요청에 같은 시스템 프롬프트를 붙이는 서비스라면 shared prefix 결과를 참고할 수 있어요. shared prefix가 80 토큰일 때 Orca (Oracle)의 1.67배였던 vLLM의 처리량이 341 토큰에서는 3.58배로 커졌으므로 시스템 프롬프트가 길수록 블록 공유로 얻는 이득도 클 수 있어요.

질문과 답이 짧고 모델 크기에 비해 GPU 메모리가 넉넉한 서비스라면 이득이 작을 수 있어요. OPT-175B와 Alpaca 조건처럼 기존 시스템도 요청을 충분히 묶을 수 있으면 성능의 상한을 GPU 연산 능력이 정하기 때문이에요.

여러 차례 주고받는 대화 서비스라면 챗봇 실험이 대화 차례 사이에 KV cache를 저장하지 않았다는 조건도 함께 확인해야 해요. Kwon 등(2023)은 대화 차례 사이에 KV cache를 남겨 두면 그동안 다른 요청이 그 공간을 사용할 수 없어서 저장하지 않았어요.

## 마치며

PagedAttention은 출력 길이를 미리 알 수 없어 메모리를 그때그때 할당해야 하고 GPU 메모리 용량이 처리량을 정하는 작업에서 효과를 냈어요. Kwon 등(2023)은 데이터 크기가 대개 고정된 모델 학습이나, LLM이 아닌 모델의 서빙처럼 성능의 상한을 주로 연산 능력이 정하는 작업에서는 이 기법으로 성능이 오르지 않을 수 있고, block table을 거치는 추가 단계 때문에 오히려 떨어질 수도 있다고 지적해요. 비교 대상인 Orca는 Kwon 등(2023)이 직접 구현하면서 buddy allocator를 사용한다고 가정했으므로 Orca와의 차이는 이 가정 위에서 측정한 값이에요. 실험은 OPT와 LLaMA 모델, NVIDIA A100 GPU, ShareGPT와 Alpaca로 만든 요청, shared prefix 실험의 WMT16 번역 데이터로 했어요.
