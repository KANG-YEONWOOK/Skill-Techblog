# dogfooding 기록

실행 조건과 평가 방법은 [README.md](README.md)에 있다. 모든 실행은 Claude Code 2.1.289, `--model opus --effort xhigh`(S3만 sonnet), 사용자 CLAUDE.md를 끈 상태다. judge는 sonnet이다.

표의 지표
- lint G/F/W: Gate 위반 / FAIL / WARN 수
- 목록, bold, 셋 묶음, 연결어미 쉼표, 부정 대구: 스킬 없는 Claude 출력이 사람 글 p90을 넘었던 지표(사람 글 p90: 목록 0.25, bold 3.23/1,000자, 셋 묶음 1.90/1,000자, 연결어미 쉼표 0.33, 부정 대구 2문장)
- 종결 반복: 같은 종결이 4문장 이상 이어진 횟수(사람 글 p90 5)
- style 평균: style judge J2~J6, J8 평균(0~2), 2회 실행
- J7/1k: style judge가 "AI가 쓴 것처럼 읽힌다"고 인용한 문장 수(1,000자당, 인용이 본문에 있는 것만)
- fidelity: 자료로 뒷받침되지 않는 주장 / 자료와 다른 주장
- pairwise: 같은 자료의 iteration 0 글과 순서를 바꿔 두 번 비교. current는 두 번 모두 이번 글을 고른 경우, split은 순서에 따라 갈린 경우

pairwise에서 A가 갈린 이유(judge 근거 요약)

- 반대 순서에서는 iteration 0 글의 요약 표지("짚어 둘 점이 세 가지 있어요"), 부정 대구, 은유("손잡이는 β 하나뿐")가 더 크게 보여 이번 글이 이겼다.

원인 분석
- 종결 반복: Casual 글은 Default 초안의 종결부만 바꾸므로 초안의 종결이 "~합니다/~했습니다"에 몰리면 Casual도 "~해요/~했어요"만 이어진다. A의 현재형 해요체 비율은 50%로 사람 해요체 글(27%)의 두 배였다.
- 도입: style-guide가 "독자 상황이나 문제에서 시작"만 정하고 수치 나열을 막지 않았다.
- 분석 부족: 스킬이 "자료에 있는 사실만"을 강조해서 자료에 근거한 해석(설계 이유, 표의 수치 비교)까지 줄었다.
- S1의 근거 없는 문장: style-guide의 "자료가 남긴 열린 질문으로 끝낸다"를 따라 자료가 열린 질문이라고 하지 않은 내용을 열린 질문으로 썼다.

## iteration 2 변경 (도입, 분석, 리듬, 용어)

- style-guide, SKILL.md

- lint
  - A8.ending_run4(같은 종결 4문장 이상 연속)를 참고 지표에서 판정 지표로 올렸다(사람 글 기준 PASS ≤6, WARN ≤10).
  - A3에 평가형 강조("~점이 흥미롭습니다", "결과는 ~ 극적입니다", "진짜 강점은") 패턴을 추가하고 사람 글로 기준치를 다시 잡았다(PASS ≤2). holdout 통과율은 86%로 같다.

## iteration 3 변경 (문장 주어, 마무리, 분석의 정보성)

- 사실은 기술·방법·결과를 주어로 쓰고 "저자들은", "논문은"은 저자의 주장·추정·판단을 옮길 때만 쓴다(본문 문장의 10% 이하). lint에 A16.source_subject_share(policy, PASS ≤0.10)를 추가했다.
- "마치며"는 3~5문장으로 쓰고 본문 수치를 다시 늘어놓지 않는다.
- 도입의 "이 글에서는 ~를 정리합니다"는 한 문장으로 쓰고 다룰 항목을 셋 이상 늘어놓지 않는다.
- 분석 문장도 deletion test를 통과해야 한다(새 수치 비교나 조건이 있어야 한다). 자료의 조건에서 추론한 내용은 추론임을 문장에 드러낸다.
- "모두", "항상", "전혀", "유일한" 같은 범위 표현은 자료가 그렇게 쓴 경우에만 쓴다.
- 셋 묶음 검출에서 수치·영문 이름·인용이 든 나열을 뺐다(사람 글로 다시 보정, PASS ≤1.62/1,000자).
- style-guide와 SKILL.md의 예시 문장에 남아 있던 테스트 자료(Antislop)의 사실을 가상 자료의 예시로 바꿨다. 예시 문장이 테스트 글에 섞여 들어가는 것을 막기 위해서다.
- 참고: rubric.md는 근거 자료로 B·C·D 케이스의 논문 수치를 인용한다. 스킬이 점검 단계에서 rubric을 읽으므로 이 세 논문을 정리할 때는 rubric의 요약이 영향을 줄 수 있다. 이 영향이 없는 자료(S1, E, S2)로도 같은 기준을 확인한다.

- style-guide와 SKILL.md에 "문장을 따로 읽어도 이해되게 쓰기" 규칙을 넣었다. 문장마다 무엇에 대한 말인지 쓰고, 수치를 쓰는 문장에는 무엇을 잰 값인지와 비교 기준을 같은 문장에 쓰게 했다.
- fact sheet 맨 위에 글의 핵심 주제를 한 문장으로 적게 했다. 제목, 도입, 각 절은 이 주제를 설명한다.
- 점검 단계에 단독 읽기 점검을 넣었다. lint가 점검 후보(A18)에 걸린 문장을 보여 주면, 스킬은 그 문장과 바로 앞 문장만 읽고 무엇에 대한 말인지 알 수 있는지 확인한다.
- rubric에 J9(문장 완결성)를 넣고 dogfooding에 clarity judge를 추가했다. clarity judge의 판정 방식은 `README.md`의 "평가 방법" 절에 있다.

## 수정 종료 판단

계획한 수정은 최대 2회였고, iteration 10에서 멈춘다.

- 충족한 것: 사용자의 요구였던 문장 완결성은 J9 21.3%에서 13.5%로 낮아져 사람 글 대조군(17.4%)보다 낮다. lint와 tone_check는 4편 모두 통과했다. pairwise는 iteration 8의 0승 2패(2쌍은 순서에 따라 갈림)에서 iteration 10의 3승 1패로 올랐다.
- 남은 문제
  - 비교 기준의 반복: 수치가 많은 글에서 같은 비교 기준과 %p 차이를 문단마다 되풀이한다(B). 고친다면 "같은 비교 기준은 절에서 처음 한 번 쓰고, 독자가 계산할 수 있는 차이는 쓰지 않는다"는 규칙이 후보다. 이 규칙은 앞 문장에 기대는 수치 문장을 늘려 J9를 높일 수 있다.
  - 단조로움(J8): J8은 iteration 4 이후 스킬 글에서 대부분 1~1.5점이었고(iteration 5는 1.5~2점) 이번에도 1점이었다. 지시문으로 한 가지 반복을 줄이면 judge가 다른 반복을 지적했다. style judge의 점수가 채점 묶음 단위로 함께 움직여서, 2회 채점으로는 0.5점 차이를 지시문 효과로 판단하기 어렵다.
  - 합니다체 글의 J9: 어투별로 보면 합니다체 skill 글(15.8%)이 사람 합니다체 글 3편(12.5%)보다 높다.
  - 수정 전 글의 fidelity 값이 없어서 fidelity 기준은 판단하지 못했다. iteration 9 글 4편은 0건, iteration 10 글 4편은 2건이었다.

## claude plugin eval (0.3.0, commit d218dd6)

`evals/`의 세 케이스를 skill이 있을 때와 없을 때 각각 2회씩, 한 번에 한 실행씩 돌렸다(Opus, grader judge Sonnet, Windows라 eval run 안에서 Bash 없음). 0.3.0에서 SKILL.md의 description을 고쳤으므로 자연어 요청으로 skill이 호출되는지도 확인했다.

- skill이 있는 6회 실행 모두에서 `/techblog` 없이 쓴 자연어 요청으로 skill이 호출됐다.
- 첫 측정의 케이스 평균은 skill 있음 0.889 / 0.889 / 1.000, skill 없음 0.667 / 0.778 / 1.000(note-casual / note-default / retone-casual)이었다. skill 없는 쪽은 4회 중 3회가 문장 안 em dash·세미콜론과 지어낸 경험 grader에서 실패했다.
- iteration 8에서 추가한 clarity grader는 note 케이스 8회(skill 있음 4회, 없음 4회)에서 모두 실패했다. grader 문구가 수치 문장 하나라도 측정 대상이나 비교 기준을 알 수 없으면 FAIL로 정했고, 비교가 아닌 수치("토큰 하나의 KV cache는 800KB입니다" 같은 문장)에도 비교 기준을 요구했다. 모든 글을 FAIL로 판정하는 grader는 skill이 있을 때와 없을 때를 구별하지 못한다. 그래서 비교 기준은 배수, 증감, 차이처럼 두 값을 비교하는 수치에만 요구하고, 바로 앞 문장까지 읽어도 무엇의 값인지 알 수 없는 수치 문장이 있을 때만 FAIL로 고쳤다. 이 기준은 rubric J9의 unclear 판정에 해당한다.
- 고친 grader로 note 두 케이스를 다시 실행했다. 백그라운드 실행이 메모리 부족으로 중단돼서, 케이스마다 skill 있음과 없음을 1회씩 포그라운드로 실행했다.
